## 2. العمليات الدورية

### يوميًا (5 دقائق)

```
□ لوحة الصحة: لا عناصر dead، لا دفعات معلّقة > 30 دقيقة
□ طلبات متوقفة في مرحلة > عتبتها
□ آخر نسخة احتياطية ناجحة
□ نسخ التطبيق النشطة — أكثر من نسختين يستدعي تدخلًا
```

### أسبوعيًا (20 دقيقة)

```
□ مراجعة audit_logs لعمليات غير معتادة
□ عدد stale_state — ارتفاعه يعني تداخلًا في العمل
□ عدد qr_mismatch — ارتفاعه يعني مشكلة في الطباعة أو التوزيع
□ نسبة نجاح OTP وواتساب
□ Supabase Advisor
□ استهلاك الموارد مقابل حدود الخطة
```

### شهريًا (ساعة)

```
□ npm audit + تحديث الاعتماديات
□ مراجعة بطء الاستعلامات (pg_stat_statements)
□ حجم قاعدة البيانات والتخزين والاتجاه
□ مراجعة سياسة الاحتفاظ والحذف المنفَّذ
□ مراجعة حسابات الموظفين — تعطيل من غادر
```

### فصليًا (نصف يوم)

```
□ اختبار استعادة كامل على مشروع مؤقت
□ تدوير الأسرار
□ مراجعة أمنية للمصفوفة والسياسات
□ مراجعة الخطة والمزايا المؤجلة
```

## 3. أدلة التعامل مع الأعطال

### 3.1 موظف: «تعذّر إتمام العملية»

```
1. اطلب منه رمز الطلب الظاهر بين قوسين (6 أحرف)
2. ابحث في سجلات الوظائف بـ request_id
3. اقرأ outcome و code:

   business_error → الرمز يفسّر نفسه، اشرح للموظف
     qr_mismatch      → الرمز ليس لعميل هذا الطلب
     payment_required → سجّل الدفع أولًا
     stale_state      → أعد تحميل الصفحة
     forbidden        → صلاحية غير كافية

   server_error   → اقرأ الاستثناء، أعد الإنتاج على staging،
                    اكتب اختبارًا يفشل، أصلح، انشر
```

### 3.2 عميل: لا يصله رمز التحقق

```
1. تحقق أن رقمه في النظام صحيح ومُوحَّد (+968XXXXXXXX)
2. otp_challenges: هل أُنشئ تحدٍّ؟
   لا  → فحص حدود المعدل (5/ساعة للعميل، 20/ساعة للـIP)
   نعم → فحص سجل الوظيفة: هل نجح النداء للجسر؟
3. اختبر صحة الجسر برسالة تجريبية
4. تحقق أن القالب order_confirmation_v2 ما زال معتمدًا
```

### 3.3 الماسح لا يعمل

```
1. هل الصفحة على HTTPS؟ (الكاميرا لا تعمل بدونها)
2. هل أُعطي الإذن؟ → إعدادات الجهاز ← المتصفح ← الكاميرا
3. هل الترويسة صحيحة؟ Permissions-Policy: camera=(self)
   → شغّل verify-headers.js
4. iPhone؟ تأكد أن الطبقة الثانية (تحليل الإطارات) تعمل
5. البديل الفوري: قارئ USB أو لصق الرابط يدويًا
```

### 3.4 طابور الإشعارات متوقف

```
1. هل مهمة pg_cron تعمل؟ select * from cron.job_run_details …
2. هل الجسر يستجيب؟ نداء صحة مباشر
3. اقرأ last_error_code في العناصر الفاشلة
4. عناصر dead: أصلح السبب ثم أعد جدولتها يدويًا
   update private.notification_outbox
      set state='pending', attempts=0, next_attempt_at=now()
    where state='dead' and id = any($1);
```

### 3.5 دفعة لا تصل رغم أن العميل دفع

```
1. payment_events للطلب — هل وصل webhook؟
   لا  → هل رابط الـwebhook مسجَّل صحيحًا في لوحة ثواني؟
2. هل مهمة المصالحة تعمل؟
3. استعلام يدوي: زر «تحقق من ثواني» في بطاقة الطلب
4. إن أكدت ثواني الدفع ولم يُطبَّق → عطل في fn_apply_payment_webhook
   → اختبار يفشل + إصلاح
5. حل مؤقت للعميل: تسجيل دفع يدوي بصلاحية manager مع سبب موثّق
```

### 3.6 موظف يرى نسخة قديمة

```
لا ينبغي أن يحدث — Service Worker يُعلن التحديث. إن حدث:
1. تحقق من نسخته في السجل (X-App-Version)
2. اطلب إغلاق كل تبويبات app.myduby.com وإعادة الفتح
3. لم ينجح؟ إعدادات الموقع ← مسح بيانات الموقع
4. حقّق في السبب — فشل SW في الإعلان عطل بحد ذاته
```

### 3.7 النظام بطيء

```
1. لوحة Supabase: استهلاك المعالج والاتصالات
2. pg_stat_statements: أبطأ الاستعلامات
3. هل فهرس مفقود؟ EXPLAIN ANALYZE على الاستعلام البطيء
4. هل عملية ثقيلة تعمل؟ (تنظيف، مصالحة)
5. هل قاربنا حدود الخطة؟
```

## 4. مهام إدارية

### إضافة موظف

```
1. المزيد ← إدارة الموظفين ← إضافة  (admin فقط)
2. بريد + اسم + دور
3. يصله رابط تعيين كلمة مرور
4. الأثر يُسجَّل في audit_logs تلقائيًا
```

### تعطيل موظف

```
1. المزيد ← إدارة الموظفين ← تعطيل
2. الأثر فوري — auth_role() تعيد null
3. لا حاجة لانتظار انتهاء الجلسة
```

### إعادة إصدار QR

```
1. العملاء ← العميل ← إعادة إصدار QR
2. سبب إلزامي
3. الرمز القديم يُبطل فورًا مع حفظ تاريخه
4. اطبع الرمز الجديد وسلّمه
5. من يمسح القديم يرى: «هذا الرمز أُبطل — اطلب رمزًا جديدًا»
```

### تصحيح خطأ في طلب

| الخطأ | التصحيح |
|---|---|
| حالة خاطئة قبل الاكتمال | لا رجوع للخلف — ألغِ الطلب بسبب وأنشئ بديلًا |
| حالة خاطئة بعد الاكتمال | مقفلة — يتطلب تدخلًا موثّقًا من `admin` على قاعدة البيانات |
| رقم فاتورة خاطئ | `admin` يعدّله مع سبب في سجل التدقيق |
| دفع مسجّل خطأً | `admin` ← إلغاء الدفع مع سبب |
| صورة خاطئة | لا حذف — الصورة دليل؛ أضف ملاحظة للطلب |

## 5. تعريفات الخطورة

| المستوى | التعريف | زمن الاستجابة | مثال |
|---|---|---|---|
| **P1** | النظام معطّل أو بيانات مفقودة | فوري | لا يمكن تسجيل الدخول؛ صفحة العميل معطّلة |
| **P2** | وظيفة أساسية معطّلة بلا بديل | ساعتان | التسليم لا يعمل؛ الدفع لا يُسجَّل |
| **P3** | وظيفة معطّلة مع بديل يدوي | يوم عمل | الماسح لا يعمل والقارئ الخارجي يعمل |
| **P4** | عيب تجميلي أو تحسين | الإصدار التالي | تنسيق، ترتيب، صياغة |

### مسار التصعيد

```
P1 → تنبيه فوري للمالك + بدء الإصلاح + تقييم التراجع خلال 15 دقيقة
P2 → إشعار + إصلاح في نفس اليوم
P3 → تذكرة + الإصدار القادم
P4 → قائمة التحسينات
```

## 6. جهات الاتصال والمراجع

| الجهة | الاستخدام |
|---|---|
| لوحة Supabase | قاعدة البيانات، الوظائف، السجلات، التخزين |
| Cloudflare Pages | نشر الواجهات، التراجع الفوري |
| لوحة ثواني | الجلسات، الـwebhook، المفاتيح |
| مزود واتساب | حالة الجسر، اعتماد القوالب |
| GitHub | الكود، الإصدارات، خط النشر |

### قبل أي تدخل مباشر على قاعدة الإنتاج

```
□ هل يمكن حله عبر واجهة التطبيق؟          → استخدمها
□ هل جُرّب على staging أولًا؟               → جرّبه
□ هل هناك نسخة احتياطية حديثة؟             → خذ واحدة
□ هل الأمر داخل معاملة قابلة للتراجع؟       → اجعله كذلك
□ هل سيُسجَّل في audit_logs؟                 → سجّله يدويًا إن لزم
```

التدخل المباشر على الإنتاج آخر الحلول لا أولها — وهو ما جعل النظام الحالي
صعب التشخيص.
