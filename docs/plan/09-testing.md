# 09 — الاختبار

## 1. لماذا هذا القسم ليس شكليًا

النظام الحالي يملك 6 اختبارات. وثلاثة من أعطاله الكبرى كان اختبارٌ واحد كافيًا
لمنع كل منها:

| العطل | الاختبار الذي كان سيمنعه |
|---|---|
| قيد `CHECK` بتعبير منتظم لا يطابق أي مسار صحيح | اختبار pgTAP: إدراج مسار صحيح ← يُقبل |
| قيدان قديمان يرفضان الانتقال الجديد | اختبار انتقال حالة كامل |
| `refreshSession()` يغلق النافذة قبل الإرسال | اختبار E2E لمسار التسليم |

لذلك تُعامل الاختبارات هنا كجزء من التعريف الهندسي، لا كخطوة لاحقة.

## 2. الهرم

```
        ┌─────────────┐
        │  E2E (17)   │  Playwright — الرحلات الحرجة على متصفح حقيقي
      ┌─┴─────────────┴─┐
      │ تكامل (~50)     │  وظائف Edge مقابل قاعدة محلية حقيقية
    ┌─┴─────────────────┴─┐
    │ قاعدة البيانات (~75)│  pgTAP — قيود، RLS، دوال، محفّزات
  ┌─┴─────────────────────┴─┐
  │   وحدة (~120)           │  منطق نقي: تحقق، تطبيع، تحويل
  └─────────────────────────┘
```

**الأثقل عمدًا في طبقة قاعدة البيانات** — لأن قواعد العمل الحرجة تعيش هناك.

## 4. اختبارات قاعدة البيانات (pgTAP)

### 4.1 القيود

```sql
-- كل قيد له اختباران: يرفض الخطأ، ويقبل الصحيح
select throws_ok(
  $$ update orders set status='completed' where id=:oid $$,
  '23514', 'الاكتمال يُرفض بلا دفع'
);

select lives_ok(
  $$ update orders set payment_status='paid', payment_method='cash_on_delivery',
            paid_at=now(), delivery_confirmed_at=now(), delivery_confirmed_by=:sid,
            status='completed' where id=:oid $$,
  'الاكتمال يُقبل مع دفع وتأكيد تسليم'
);
```

| القيد | يرفض | يقبل |
|---|---|---|
| `orders_completed_requires_payment` | اكتمال بلا دفع | اكتمال مع دفع |
| `orders_completed_requires_delivery` | اكتمال بلا تأكيد تسليم | مع تأكيد |
| `orders_picked_up_requires_confirmation` | استلام بلا تأكيد | مع تأكيد |
| `orders_payment_consistent` | `paid` بلا طريقة ووقت | متسق |
| `orders_invoice_complete` | رقم بلا قيمة | كامل |
| `orders_invoice_no_idx` | رقم فاتورة مكرر | رقم فريد |
| `orders_cancel_requires_reason` | إلغاء بلا سبب | مع سبب |
| `customers_complete_requires_fields` | `complete` بحقل ناقص | كامل |
| `customer_qr_active_idx` | رمزان فعّالان لعميل | رمز فعّال واحد |
| `order_photos_kind_idx` | صورتان من نوع واحد | واحدة |
| `payments.provider_session_id` | جلسة مكررة | فريدة |
| `cash_settlement_no_self_verify` | `verified_by = courier_id` | مدقّق مختلف |
| `cash_settlement_no_self_approve` | `approved_by = courier_id` | معتمِد مختلف |
| `cash_settlement_variance_needs_reason` | فرق بلا سبب | مع سبب |
| `cash_settlement_deposit_needs_proof` | إيداع بنكي بلا صورة إثبات | مع إثبات |
| `cash_settlement_handover_complete` | تسليم بلا طريقة أو وقت | كامل |
| `cash_settlement_large_variance_needs_approval` | فرق كبير بلا اعتماد | مع اعتماد |
| `cash_settlement_one_per_day` | تسويتان لمندوب في يوم | واحدة |
| `cash_collections_active_order_idx` | تحصيلان لطلب واحد | واحد |

### 4.2 مصفوفة الانتقالات

اختبار مولَّد يغطي **كل** خانة في مصفوفة [04-domain-flows.md](04-domain-flows.md):
8 حالات × 8 حالات = 64 حالة اختبار، كل واحدة تتحقق من القبول أو الرفض.

```sql
-- عينة من الخانات المرفوضة
select throws_ok($$ … new → picked_up      $$, 'قفزة فوق التأكيد مرفوضة');
select throws_ok($$ … ready → completed    $$, 'قفزة فوق التوصيل مرفوضة');
select throws_ok($$ … completed → anything $$, 'الحالة النهائية مقفلة');
select throws_ok($$ … cancelled → new      $$, 'الملغي لا يُحيا');
```

### 4.3 سياسات RLS

لكل جدول ولكل دور:

```sql
set local role authenticated;
set local request.jwt.claims to '{"sub":"<operator-uuid>"}';

select is_empty($$ select * from otp_challenges $$, 'operator لا يقرأ التحديات');
select isnt_empty($$ select * from orders $$,        'operator يقرأ الطلبات');
select throws_ok($$ update orders set status='completed' $$,
                 'الواجهة لا تكتب على الطلبات مباشرة');
```

| الفحص | التوقع |
|---|---|
| `anon` على كل جدول | صفر صفوف |
| `authenticated` على `otp_challenges` | صفر صفوف |
| `authenticated` على `order_submissions` | صفر صفوف |
| `authenticated` على `private.*` | خطأ صلاحية |
| `authenticated` كتابة على أي جدول | مرفوضة |
| موظف معطَّل | `auth_role()` = null ← كل شيء مرفوض |

### 4.4 الدوال

| الدالة | حالات الاختبار |
|---|---|
| `fn_confirm_field_step` | نجاح، `qr_mismatch`، `payment_required`، `stale_state`، موظف معطَّل، صورة مكررة، تنفيذان متزامنان |
| `fn_verify_otp` | نجاح، رمز خاطئ، منتهٍ، تجاوز المحاولات، رمز مُبطل |
| `fn_submit_order` | نجاح، رمز مستهلَك، منتهٍ، إعادة إرسال ← نفس الطلب |
| `fn_create_invoice` | نجاح، رقم مكرر، قيمة سالبة، حالة خاطئة |
| `fn_record_cash_payment` | المندوب ينجح، يفتح تسوية اليوم، يحدّث `expected_amount`؛ يُرفض عند تسوية متأخرة |
| `fn_hand_over_settlement` | صاحبها ينجح؛ غيره يُرفض؛ إيداع بلا إثبات يُرفض؛ **إثبات مكرر يُرفض**؛ بعدها لا تحصيلات جديدة |
| `fn_verify_settlement` | `operator` لغيره ينجح؛ **لنفسه يُرفض**؛ `courier` يُرفض؛ فرق كبير ← `disputed` |
| `fn_match_bank_deposit` | ينجح على تسوية معتمدة؛ أي تعديل آخر عليها يُرفض |
| `fn_approve_variance` | `manager` ينجح، `operator` يُرفض، المندوب نفسه يُرفض |
| `fn_reverse_cash_collection` | قبل الاعتماد ينجح، بعده يُرفض |
| `fn_reverse_payment` | `admin` ينجح، دفع ثواني مؤكد يُرفض |
| `fn_complete_profile` | `property_id` وارد **يُتجاهل** |

## 5. اختبارات التكامل

تعمل على Supabase محلي في CI (`supabase start`)، بمزودين مزيّفين.

| المجموعة | التغطية |
|---|---|
| `public-qr` | كل نقطة نهاية × كل رمز خطأ في العقد |
| `staff-orders` | المسارات الميدانية، الصلاحيات، التزامن |
| `payments` | الفوترة، الاستعلام، النقدي، الإلغاء |
| `payments-webhook` | توقيع صالح، غير صالح، مفقود، تكرار |
| `settlements` | التسليم، الإثبات، الاعتماد عن بُعد، اعتماد الذات، الفرق الكبير، المطابقة البنكية |
| `notifications` | سحب الطابور، نجاح، فشل، تراجع، `dead` |
| `admin` | إدارة الموظفين، الإعدادات، التدقيق |

**قاعدة**: كل رمز خطأ مذكور في [05-api-contracts.md](05-api-contracts.md) له اختبار
يُنتجه. رمز بلا اختبار = رمز غير موجود فعليًا.

## 6. اختبارات E2E

Playwright، على Chromium وWebKit (لتغطية سلوك Safari).

| # | السيناريو | الخطوات |
|---|---|---|
| E1 | رحلة عميل جديد | مسح ← بيانات ← OTP ← صورة ← طلب |
| E2 | رحلة عميل مكتمل | مسح ← OTP ← صورة ← طلب |
| E3 | دورة طلب كاملة | من `new` إلى `completed` عبر كل المراحل |
| E4 | الاستلام الميداني | QR + صورة ← `picked_up` |
| E5 | **التسليم بلا دفع** | الزر معطّل ← تسجيل نقدي ← الزر يعمل |
| E6 | **QR خاطئ عند التسليم** | خطأ في النافذة، النافذة تبقى، الحالة لا تتغير |
| E7 | مسار الدفع | فاتورة ← رابط ← webhook ← `paid` |
| E8 | الصلاحيات | `operator` لا يرى زر الدفع النقدي ويُرفض عند الاستدعاء المباشر |
| E9 | الإلغاء | سبب إلزامي، الزر يختفي بعد الاكتمال |
| E10 | **تخطيط الجوال** | فتح لوحة المفاتيح ← الأبعاد ثابتة، الأزرار ظاهرة |
| E11 | **ماسح الكاميرا** | تشغيل، قراءة، إيقاف المسارات عند الإغلاق |
| E12 | تعارض موظفَين | تحديث متزامن ← الثاني يحصل على `stale_state` |
| E13 | **دورة التسوية اليومية** | مندوب يحصّل 3 مرات ← يسلّم بإيداع بنكي وصورة ← `operator` يعتمد عن بُعد ← الفرق صفر |
| E14 | **رفض اعتماد الذات** | `operator` يحاول اعتماد تسويته ← الزر غائب **والخادم يرفض الاستدعاء المباشر** |
| E15 | **حجب التحصيل عند عدم التسليم** | تسوية `open` > الحد ← زر النقد معطّل ← بعد التسليم يعمل **فورًا دون انتظار الاعتماد** |
| E17 | **رفض الإثبات المُعاد** | رفع نفس صورة الإيصال في تسوية تالية ← `proof_reused` |
| E16 | الفرق خارج السماح | عجز كبير ← `disputed` ← `manager` يعتمد بسبب |

الصفوف الغامقة هي **اختبارات منع تراجع** لأعطال وقعت فعلًا. لا يُدمج تغيير
يكسر أيًا منها.

## 7. اختبارات غير وظيفية

| النوع | الأداة | البوابة |
|---|---|---|
| أداء الحزمة | Lighthouse CI | الأداء ≥ 85، إمكانية الوصول ≥ 95 |
| حجم الحزمة | `size-limit` | موظفون ≤ 300KB، عميل ≤ 120KB |
| ضغط | k6 | 50 مسحًا متزامنًا، p95 < 1s |
| الأمن | `gitleaks`, `npm audit`, Supabase Advisor | صفر تحذيرات عالية |
| الترويسات | فحص بعد النشر | مطابقة كاملة لمواصفة `_headers` |
| الاستعادة | يدوي فصلي | استعادة كاملة موثّقة بالزمن |

## 9. بوابات الجودة في CI

لا يُدمج إلى `main` قبل اجتياز:

```
✓ فحص الأنواع (tsc --noEmit)
✓ Lint + تنسيق
✓ اختبارات الوحدة              تغطية ≥ 80% للمنطق
✓ pgTAP                        100% من القيود والسياسات
✓ اختبارات التكامل             100% من رموز الأخطاء
✓ E2E                          كل الـ17 خضراء
✓ حجم الحزمة ضمن الحد
✓ gitleaks + npm audit
✓ توليد الأنواع لا ينتج فرقًا   (المخطط والأنواع متزامنان)
```

**قاعدة**: أي عطل إنتاج يُصلَح باختبار يفشل أولًا ثم إصلاح يجعله يمر. الإصلاح بلا
اختبار مرفوض في المراجعة.
