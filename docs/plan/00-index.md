## الملخص التنفيذي

### ما الذي يتغيّر جوهريًا

النظام الحالي يعمل، لكن أعطاله لم تكن في منطق الأعمال — كانت في **حدود النظام**:
تباعد نسخ الواجهة، Service Worker يخدم ملفًا قديمًا، ترويسات استضافة تكسر
الاتصال والكاميرا بصمت، وقيود قاعدة بيانات تتباعد عن الكود. لذلك تبدأ الخطة من
هذه الحدود لا من المزايا:

| النظام الحالي | النظام الجديد |
|---|---|
| ملف HTML واحد ~680KB يُرفع يدويًا بالـFTP | تطبيق PWA يُبنى ويُنشر آليًا من Git |
| ثلاث نسخ متنافسة من الواجهة | مصدر حقيقة واحد في المستودع |
| Edge Function واحدة >1300 سطر | خمس وحدات مفصولة بمسؤوليات واضحة |
| استضافة GoDaddy تفرض CSP و`camera=()` | استضافة ثابتة نتحكم في ترويساتها بالكامل |
| لا Git، لا CI، لا بيئة اختبار | مستودع + CI + بيئة `staging` مطابقة |
| 6 اختبارات آلية | مصفوفة اختبار تغطي RLS والدفع والمسار الكامل |
| الأدوار موجودة اسمًا لا فعلًا | صلاحيات مفروضة في ثلاث طبقات |
| هجرات تُطبَّق يدويًا على الإنتاج | هجرات مُصدَّرة في Git، تمر عبر `staging` أولًا |

### ما الذي يبقى

ليس كل شيء يستحق الاستبدال. يُحتفظ بما ثبتت جودته:

- **PostgreSQL + RLS** كخط دفاع أخير — قواعد العمل الحرجة تبقى في قاعدة البيانات.
- **العمليات الذرّية** للاستلام والتسليم — الدرس الأغلى في المشروع كله.
- **تصميم QR**: رابط + UUID عشوائي، بلا أي بيانات شخصية.
- **OTP مجزّأ بـ HMAC** مع pepper، لا يُخزَّن نصًّا أبدًا.
- **حاوية تخزين خاصة** للصور مع روابط موقّعة قصيرة الصلاحية.
- **قاعدة منع التسليم قبل الدفع** مفروضة في قاعدة البيانات.

### الحزمة التقنية المعتمدة

```
TypeScript في كل الطبقات
├── قاعدة البيانات    PostgreSQL 15 على Supabase + RLS + هجرات في Git
├── المصادقة          Supabase Auth (موظفون فقط)
├── التخزين           Supabase Storage — حاويات خاصة
├── الخلفية           Supabase Edge Functions (Deno) — 5 وحدات مفصولة
├── تطبيق الموظفين    React + Vite + PWA
├── صفحة العميل       React + Vite — حزمة منفصلة خفيفة
├── الاستضافة         Cloudflare Pages (نطاقات فرعية على myduby.com)
├── المستودع          monorepo واحد + pnpm workspaces
└── CI/CD             GitHub Actions
```

**لماذا لا GoDaddy**: الاستضافة الحالية أنتجت ثلاثة أعطال مستقلة (CSP يمنع
Supabase، `Permissions-Policy: camera=()` يعطّل الماسح، Service Worker يخدم نسخة
قديمة). الحل ليس المزيد من تعديلات `.htaccess` — الحل استضافة ثابتة نملك فيها
ترويساتها ونشرها وإبطال الكاش. GoDaddy تبقى للنطاق وجسر واتساب فقط.

التفاصيل والبدائل المدروسة في [المعمارية](02-architecture.md).

### الجدول الزمني

| المرحلة | المدة | المخرج |
|---|---|---|
| 0 — التأسيس | أسبوع 1 | مستودع، CI، بيئات، هيكل يعمل من طرف إلى طرف |
| 1 — النواة | أسبوعان | قاعدة البيانات، المصادقة، RLS، العقارات، العملاء، QR |
| 2 — رحلة العميل | أسبوعان | مسح، OTP، تصوير، إنشاء الطلب |
| 3 — لوحة الموظفين | 3 أسابيع | PWA، دورة حياة الطلب، الاستلام والتسليم الميداني |
| 4 — الفوترة والدفع | أسبوعان | ثواني، webhook، مصالحة، الدفع النقدي |
| 5 — الإشعارات | أسبوع | Outbox، واتساب، إعادة المحاولة (يتوازى مع 3–4) |
| 6 — التقارير | أسبوعان | التحليلات التشغيلية ولوحة المؤشرات |
| 7 — الترحيل والإطلاق | أسبوع | نقل البيانات، تشغيل متوازٍ، الإطلاق |

### قبل كل شيء — إجراءات عاجلة على النظام الحالي

هذه لا تنتظر الخطة، وتُنفَّذ خلال أيام لأن النظام الحالي يعمل في الإنتاج الآن:

1. جعل رابط محادثة ChatGPT خاصًا، واعتبار كل ما ظهر فيه منكشفًا.
2. تدوير كل المفاتيح: مفتاح `qr-admin-builder`، وأسرار واتساب وثواني.
3. تعطيل وحذف وظيفة `qr-admin-builder` نهائيًا.
4. نسخة احتياطية كاملة (قاعدة + تخزين) والتحقق من قابلية الاستعادة.
5. تفعيل حماية كلمات المرور المسرّبة، وتأكيد `ALLOW_DEBUG_OTP=false`.

التفاصيل في [`../system-analysis.md`](../system-analysis.md) القسم 10.
