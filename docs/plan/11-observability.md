# 11 — قابلية الملاحظة

## 1. المشكلة التي يحلّها هذا القسم

في النظام الحالي، تشخيص عطل واحد استهلك ست جولات لأن السؤال الأول — **هل وصل
الطلب إلى الخادم أصلًا؟** — لم يكن له جواب. أُضيف تتبع مؤقت، فظهر السجل فارغًا،
وهذه المعلومة وحدها قلبت مسار التشخيص كاملًا.

الهدف هنا: **لا يبدأ تشخيص بإضافة تتبع**. التتبع موجود دائمًا.

---

## 2. السجلات المنظّمة

كل سطر سجل من كل وظيفة بهذا الشكل:

```jsonc
{
  "ts": "2026-09-16T09:12:44.318Z",
  "level": "info",
  "fn": "staff-orders",
  "route": "/field-step",
  "request_id": "a3f19c4e",
  "actor_id": "…",            // معرّف الموظف، لا اسمه
  "actor_role": "operator",
  "order_id": "…",
  "step": "delivery",
  "outcome": "ok",            // ok | business_error | server_error
  "code": null,
  "duration_ms": 412,
  "app_version": "1.4.2"
}
```

### قواعد ملزمة

1. **كل** طلب يُسجَّل — الناجح والفاشل على السواء. سجل الفشل وحده لا يجيب «هل وصل؟».
2. حقول ثابتة في كل سطر: `request_id`, `fn`, `route`, `outcome`, `duration_ms`.
3. **ممنوع تسجيله**: رمز OTP، رمز QR كاملًا (البادئة فقط)، الهاتف كاملًا، أي مفتاح، جسم صورة.
4. الهاتف يُسجَّل مُقنَّعًا: `+968****23`.
5. `request_id` يولّده العميل ويمر عبر كل الطبقات إلى `order_status_history.request_id`.

### مستويات التسجيل

| المستوى | الاستخدام |
|---|---|
| `debug` | تطوير محلي فقط — لا يظهر في الإنتاج |
| `info` | كل طلب، كل تغيّر حالة، كل إرسال إشعار |
| `warn` | خطأ عمل متوقع: `qr_mismatch`, `rate_limited`, `stale_state` |
| `error` | عطل غير متوقع، فشل مزود، استثناء |

## 3. الأحداث المرصودة في قاعدة البيانات

السجلات تُقتطع بعد فترة؛ هذه الجداول هي الذاكرة الدائمة:

| الجدول | ما يجيب عنه |
|---|---|
| `scan_events` | كم مسحة، وأين توقف العملاء بالضبط |
| `order_status_history` | من غيّر ماذا ومتى وبأي `request_id` |
| `payment_events` | كل حركة مالية ومصدرها |
| `private.notification_outbox` | ماذا أُرسل وماذا فشل وكم مرة |
| `cash_settlements` + `cash_collections` | من حصّل كم، ومن اعتمد، وما الفرق |
| `private.audit_logs` | كل عملية حساسة |

سؤال نموذجي: «لماذا لم يصل إشعار لهذا العميل؟» ← استعلام واحد على الطابور يعطي
الحالة وعدد المحاولات ورمز الخطأ الأخير.

## 4. المقاييس

### مقاييس المنتج

| المقياس | الحساب | الهدف |
|---|---|---|
| نسبة التحويل من مسح إلى طلب | `order_submitted / scanned` | > 70% |
| نسبة نجاح OTP | `verified / otp_requested` | > 90% |
| زمن الطلب الكامل | `completed_at − created_at` | وسيط < 48 ساعة |
| زمن كل مرحلة | فرق التوقيتات في السجل | مراقبة الاتجاه |
| الطلبات المتأخرة | في نفس الحالة > عتبة الحالة | < 5% |
| نسبة الإلغاء | `cancelled / total` | < 5% |

### مقاييس تقنية

| المقياس | الهدف |
|---|---|
| زمن استجابة `/field-step` (p95) | < 1500ms |
| زمن قراءة الطلبات (p95) | < 500ms |
| نسبة `server_error` | < 0.5% |
| نسبة فشل واتساب | < 5% |
| عمق طابور الإشعارات | < 20 |
| عناصر `dead` في الطابور | 0 |
| زمن الاستجابة من ثواني (p95) | < 3s |

### مقاييس الجودة التشغيلية

| المقياس | لماذا يهم |
|---|---|
| عدد `stale_state` يوميًا | ارتفاعه = موظفان يعملان على نفس الطلبات |
| عدد `qr_mismatch` يوميًا | ارتفاعه = مشكلة في الطباعة أو التوزيع |
| عدد `revoked_qr` | عملاء يحملون رموزًا قديمة |
| نسخ التطبيق النشطة | من `X-App-Version` — أكثر من نسختين = مشكلة تحديث |
| النقد غير المودَع الإجمالي | ارتفاعه = تراكم التزام مالي خارج البنك |
| متوسط الفرق لكل مندوب | نمط متكرر يستدعي مراجعة إدارية لا تقنية |
| فجوة الإيداع لكل مندوب | الزمن بين آخر تحصيل والإيداع — اتساعها المتكرر مؤشر |
| **نسبة استثناءات الإيداع** | ارتفاعها = الإيداع البنكي لم يعد الطريقة الفعلية |
| تسويات مسلَّمة بانتظار الاعتماد > SLA | **مؤشر على المدقّق لا على المندوب** |
| إيداعات معتمدة بلا مطابقة بنكية | فجوة بين الإثبات والحقيقة البنكية — **المؤشر الأهم** |

| A16 | **إيداع معتمد بلا مطابقة > `cash.bank_match_sla_days`** | **عالية** | تحقيق فوري — الإيداع قد لا يكون وصل |
| A17 | نسبة استثناءات الإيداع > 20% في شهر | متوسطة | مراجعة: هل البنك غير متاح فعلًا؟ |

تقرير يومي (منخفضة).

## 6. لوحة الصحة التشغيلية

شاشة داخل التطبيق لدور `admin`:

```
┌─ اليوم ──────────────────────────────────┐
│ الطلبات: 14   المسحات: 19   التحويل: 74% │
│ نجاح OTP: 95%   نجاح واتساب: 100%        │
├─ الحالة الآن ────────────────────────────┤
│ طابور الإشعارات: 2 معلّق، 0 فاشل         │
│ دفعات معلّقة: 1                          │
├─ الصندوق ────────────────────────────────┤
│ نقد غير مودَع: 18.750 ر.ع (مندوب واحد)   │
│ بانتظار الاعتماد: 2  (أقدمها 14 ساعة)    │
│ متنازع عليها: 0                          │
│ إيداعات بلا مطابقة بنكية: 3 ⚠            │
│ استثناءات الإيداع هذا الشهر: 1 من 24     │
│ طلبات متأخرة: 0                          │
│ آخر نسخة احتياطية: قبل 6 ساعات ✓        │
├─ نسخ التطبيق النشطة ────────────────────┤
│ 1.4.2: 4 أجهزة   1.4.1: 1 جهاز ⚠        │
└──────────────────────────────────────────┘
```

عمود «نسخ التطبيق» يحل مباشرة مشكلة النظام الحالي: موظفون يعملون على نسخ مختلفة
دون أن يعرف أحد.

## 7. دفتر التشخيص

### من بلاغ مستخدم إلى سبب جذري

```
المستخدم: «تعذّر إتمام العملية (a3f19c)»
   ↓
1. بحث في سجلات الوظائف عن request_id = a3f19c4e
   → المسار، الدور، الرمز، الزمن، الحالة
   ↓
2. إن كان business_error → الرمز يفسّر نفسه
   إن كان server_error   → الاستثناء وأثر المكدس
   ↓
3. order_status_history للطلب → ما تغيّر فعلًا
   ↓
4. audit_logs بنفس request_id → السياق الكامل
   ↓
5. إعادة الإنتاج على staging بنفس المدخلات
   ↓
6. اختبار يفشل → إصلاح → الاختبار يمر
```

### أسئلة يجب أن تُجاب في أقل من دقيقة

| السؤال | المصدر |
|---|---|
| هل وصل الطلب إلى الخادم؟ | سجل الوظيفة بـ`request_id` |
| ما الحالة الفعلية للطلب الآن؟ | `orders` |
| من غيّرها آخر مرة ومتى؟ | `order_status_history` |
| هل أُرسل الإشعار؟ | `notification_outbox` |
| هل وصل الدفع من ثواني؟ | `payment_events` |
| كم بذمة هذا المندوب الآن؟ | `cash_settlements` بحالة `open` |
| من اعتمد تسوية أمس ولماذا كان فيها فرق؟ | `cash_settlements.verified_by` + `variance_reason` |
| أي نسخة يستخدم هذا الموظف؟ | `X-App-Version` في السجل |
| كم مرة تكرر هذا الخطأ اليوم؟ | تجميع على `code` |

النظام الحالي لا يجيب عن الأول ولا الأخير. وهما بالضبط السؤالان اللذان كانا
سيختصران معظم دورات التشخيص.
