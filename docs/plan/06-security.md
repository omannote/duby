# 06 — الأمن والصلاحيات

## 1. نموذج التهديد

### الأصول المحمية

| الأصل | الحساسية | أثر الانكشاف |
|---|---|---|
| بيانات العملاء (اسم، هاتف، عقار، شقة) | عالية | خصوصية — يكشف مكان سكن أشخاص حقيقيين |
| صور الطلبات | عالية | تصوير داخل منازل |
| حالة الطلب والدفع | متوسطة | تلاعب مالي |
| رموز QR | عالية | انتحال عميل وإنشاء طلبات باسمه |
| رموز OTP | حرجة | تجاوز التحقق |
| مفاتيح واتساب وثواني | حرجة | إساءة استخدام على حسابنا وبتكلفتنا |
| `service_role` key | حرجة | تجاوز RLS بالكامل |

### الخصوم المفترضون

| # | الخصم | القدرة | الضوابط المقابلة |
|---|---|---|---|
| A1 | زائر يخمّن روابط QR | مسح عشوائي لنطاق UUID | UUIDv4 = 2¹²² احتمال؛ حد معدل؛ تسجيل المحاولات |
| A2 | عميل يعدّل JavaScript في متصفحه | تعديل أي طلب من صفحة العميل | العقار من سجل العميل فقط؛ كل قاعدة في قاعدة البيانات |
| A3 | موظف يريد تجاوز صلاحيته | استدعاء أي نقطة نهاية | فحص الدور داخل كل دالة، لا في الواجهة |
| A3b | **مندوب يحتفظ بنقد أو يعلن أقل مما حصّل** | تسجيل تحصيلات ثم إعلان مبلغ أقل | `expected_amount` محسوب من النظام؛ الفرق ظاهر آليًا؛ اعتماد مستقل؛ تاريخ فروق لكل مندوب |
| A3c | **مندوب يعتمد تسويته بنفسه** | امتلاك دور أعلى أيضًا | قيد `CHECK` يرفض `verified_by = courier_id` — لا استثناء لأي دور |
| A4 | موظف سابق لم يُحذف حسابه | جلسة قائمة | `auth_role()` تعيد `null` للمعطَّل ← كل السياسات ترفض |
| A5 | من يعثر على رمز QR مطبوع | مسح رمز ليس له | OTP على هاتف صاحب الرمز المسجّل |
| A6 | مهاجم على الشبكة | اعتراض الطلبات | HTTPS إجباري، HSTS، لا أسرار في الواجهة |
| A7 | جهاز موظف مفقود | جلسة مفتوحة | انتهاء صلاحية الجلسة، تعطيل فوري من لوحة الإدارة |
| A8 | مزود خارجي مخترق | حمولات خبيثة | تحقق من التوقيع، تحقق من المخطط، لا تنفيذ للحمولة |

> **الضابط الأساسي**: المندوب يسجّل النقد لأنه من استلمه فعلًا — تقييد ذلك كان
> سيخلق وسيطًا يضيع بينه وبين النظام. لكن التسجيل يُنشئ **التزامًا ماليًا باسمه**
> تغلقه التسوية اليومية، ويعتمدها شخص آخر من `operator` فأعلى.
>
> القاعدة التي لا استثناء لها: **لا يعتمد أحد تسويته هو**، ولو كان `admin`.
> هذا مفروض بقيد `CHECK` في قاعدة البيانات، لا بإخفاء زر.

### فرض الصلاحية في ثلاث طبقات

```
1. الواجهة    → إخفاء أو تعطيل الأزرار   (تجربة استخدام، ليست حماية)
2. الدالة      → فحص auth_role() صراحةً    (الفرض الحقيقي)
3. قاعدة البيانات → RLS + قيود CHECK        (خط الدفاع الأخير)
```

نموذج الطبقة الثانية:

```sql
create or replace function fn_record_cash_payment(p_order_id uuid)
returns jsonb language plpgsql security definer set search_path = public as $$
declare v_role staff_role := auth_role();
begin
  if v_role is null or v_role not in ('manager','admin') then
    return jsonb_build_object('ok', false, 'code', 'forbidden');
  end if;
  -- …
end $$;
```

## 3. إدارة الأسرار

### أين يعيش كل سر

| السر | المكان الوحيد | يصل للمتصفح؟ |
|---|---|---|
| `SUPABASE_ANON_KEY` | حزمة الواجهة | **نعم** — أمانه من RLS وحده |
| `SUPABASE_SERVICE_ROLE_KEY` | أسرار Edge Functions | لا، أبدًا |
| `OTP_PEPPER` | أسرار Edge Functions | لا |
| `WHATSAPP_BRIDGE_API_KEY` | أسرار Edge Functions | لا |
| `THAWANI_SECRET_KEY` | أسرار Edge Functions | لا |
| `THAWANI_WEBHOOK_SECRET` | أسرار Edge Functions | لا |
| بيانات النشر | GitHub Environments | لا |

### قواعد

1. لا سر في المستودع — `gitleaks` في CI يمنع الدمج.
2. لا سر في حزمة الواجهة — فحص آلي على مخرجات البناء يبحث عن أنماط المفاتيح.
3. تدوير ربع سنوي، وفوري عند أي اشتباه.
4. الأسرار مختلفة كليًا بين `staging` والإنتاج.
5. لا سر في رابط استعلام (`?key=…`) — الروابط تُسجَّل في كل وسيط بينك وبين الخادم.

> **درس مباشر**: `qr-admin-builder` في النظام الحالي تُستدعى بمفتاح في رابط
> الاستعلام، وهذا الرابط ظهر في محادثة مشاركة علنية. النمط نفسه ممنوع هنا.

## 4. ضوابط الحماية

### حدود المعدل

| المسار | الحد | المفتاح |
|---|---|---|
| `POST /scan` | 60/دقيقة | `ip_hash` |
| `POST /request-otp` | 5/ساعة | `customer_id` |
| `POST /request-otp` | 20/ساعة | `ip_hash` |
| `POST /verify-otp` | 5 محاولات لكل تحدٍّ | `challenge_id` |
| `POST /submit-order` | 10/ساعة | `customer_id` |
| `POST /field-step` | 60/ساعة | `staff_id` |
| `POST /cash` | 60/ساعة | `staff_id` |
| `POST /settlements/*/verify` | 30/ساعة | `staff_id` |
| تسجيل الدخول | 10/ساعة ثم قفل 15 دقيقة | البريد + `ip_hash` |

### ترويسات الأمن (في `_headers` بالمستودع)

```
/*
  Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
  X-Content-Type-Options: nosniff
  X-Frame-Options: DENY
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: camera=(self), microphone=(), geolocation=(self), payment=()
  Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self' https://PROJECT.supabase.co wss://PROJECT.supabase.co; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
```

ثلاث ملاحظات:

- `camera=(self)` صريح — الاستضافة الحالية أرسلت `camera=()` فعطّلت الماسح
  وظهر العطل كأنه «المتصفح لا يدعم المسح».
- `script-src 'self'` بلا `'unsafe-inline'` — ممكن لأن البناء بـVite يخرج ملفات
  منفصلة. النظام الحالي احتاج `'unsafe-inline'` لأنه ملف واحد.
- لا CDN خارجي إطلاقًا؛ كل المكتبات مُجمَّعة في الحزمة.

### التحقق من المدخلات

مخططات Zod في `packages/shared` مستخدمة في الواجهة **وفي** الوظيفة. التحقق في
الواجهة لتجربة الاستخدام، وفي الخادم للحماية — بنفس المخطط فلا يتباعدان.

### التعامل مع الصور

| الطبقة | الفحص |
|---|---|
| المتصفح | ضغط إلى JPEG، ضلع ≤1600px، هدف <1.5MB |
| رابط الرفع | تحديد `content-type` و`byte_size` مسبقًا |
| Storage | حاوية خاصة، حد 2MB |
| الوظيفة | فحص البايتات الافتتاحية (`FF D8 FF`)، مطابقة `sha256`، رفض إعادة الاستخدام |
| قاعدة البيانات | `byte_size` في نطاق مسموح، فريدة لكل (طلب، نوع) |

### الجلسات

- انتهاء صلاحية رمز الوصول: ساعة واحدة، مع تجديد تلقائي في الخلفية.
- **قاعدة صريحة**: `refreshSession()` لا يُستدعى في معالج أي زر — التجديد يقع
  في طبقة العميل فقط، بعيدًا عن دورة حياة واجهة المستخدم.
- تعطيل الموظف يُبطل قدرته فورًا عبر `auth_role()`، دون انتظار انتهاء الجلسة.
- زر تسجيل خروج ظاهر دائمًا يمسح الجلسة والتخزين المحلي.

## 5. الخصوصية

| المبدأ | التطبيق |
|---|---|
| تقليل البيانات | QR لا يحمل شيئًا سوى UUID؛ صفحة العميل لا تعرض بياناته |
| إخفاء الهوية | IP يُخزَّن مجزَّأً بـpepper، لا صريحًا |
| الإقناع | الهاتف يُعرض `+968 ****23` في كل الواجهات العامة |
| تحديد المدة | صور تُحذف بعد 180 يومًا؛ OTP بعد 90 |
| القصر على الحاجة | `otp_challenges` و`order_submissions` لا يقرأها أحد — ولا الموظف |
| الشفافية | نص قصير في صفحة العميل: ما نجمعه ولماذا ولكم من الوقت |

## 6. الاستجابة للحوادث

| الحادث | الإجراء الفوري |
|---|---|
| تسريب `service_role` | تدوير المفتاح، مراجعة `audit_logs` للفترة، إشعار المالك |
| اختراق حساب موظف | تعطيله من لوحة الإدارة (فوري)، مراجعة عملياته، تدوير كلمة المرور |
| رمز QR منتشر خارج نطاقه | `fn_reissue_qr` مع سبب، وطباعة رمز بديل |
| إساءة استخدام واتساب | تدوير مفتاح الجسر، تشديد حدود المعدل |
| تلاعب مالي مشتبه | استخراج `payment_events` و`audit_logs` للفترة والموظف |

### دفتر التشخيص

كل حادث يبدأ من `request_id` الظاهر للمستخدم:

```
request_id → سجل الوظيفة (المسار، الدور، الرمز، الزمن)
           → audit_logs (ما تغيّر ومن غيّره)
           → order_status_history (الحالة قبل وبعد)
           → payment_events (إن كان ماليًا)
```

## 7. قائمة فحص ما قبل الإطلاق

- [ ] RLS مفعّل على كل جداول `public`، وموثّق أن `anon` لا يقرأ شيئًا.
- [ ] لا سياسات كتابة لـ`authenticated` على أي جدول.
- [ ] كل دالة `SECURITY DEFINER` تفحص `auth_role()` في سطرها الأول.
- [ ] كل دالة `SECURITY DEFINER` تضبط `search_path = public`.
- [ ] `verify_jwt=true` على كل وظيفة عدا `public-qr` و`payments-webhook`.
- [ ] CORS مقيّد لكل وظيفة إلى نطاقها.
- [ ] حماية كلمات المرور المسرّبة مفعّلة في Supabase Auth.
- [ ] `ALLOW_DEBUG_OTP` غير موجود في الإنتاج أصلًا.
- [ ] `gitleaks` أخضر، وفحص حزمة الواجهة لا يجد مفاتيح.
- [ ] Supabase Security Advisor بلا تحذيرات.
- [ ] `npm audit` بلا ثغرات عالية أو حرجة.
- [ ] حاوية `order-photos` خاصة ولا سياسات وصول عامة.
- [ ] الترويسات مطابقة للمواصفة (فحص آلي بعد النشر).
- [ ] قيد «لا اعتماد ذاتي» للتسوية مُختبَر بمحاولة فعلية لكل دور.
- [ ] `expected_amount` غير قابل للكتابة من أي نقطة نهاية.
- [ ] كل رمز خطأ في العقد له اختبار.
- [ ] نسخة احتياطية مُختبرة بالاستعادة فعليًا.
