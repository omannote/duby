# المرحلة 7 — قوائم الترحيل والإطلاق

وثيقة تنفيذية لا تخطيطية: ما يُفتح ليلة التحويل ويُعلَّم بندًا بندًا. الخلفية
والقرارات في [13-migration.md](13-migration.md)، والتشغيل اليومي بعد الإطلاق في
[14-runbook.md](14-runbook.md).

---

## 0. ما هو مُنجَز آليًا وما يبقى بشريًا

| البند | الحالة |
|---|---|
| سكربتات الترحيل | مكتوبة ومُختبَرة — `pnpm test:migration` يشغّل الدورة كاملة |
| خريطة الحالات (`delivered` بالمعنيين) | منفَّذة ومُختبَرة على كل حالة |
| التحقق بالأعداد والمجاميع | `05-verify.sql` — بوابة ترفع استثناءً عند أي فرق |
| التراجع | `06-rollback.sql` — مُختبَر، مع حارس يرفض المحو بعد أي نشاط جديد |
| بوابة جاهزية الإطلاق | `fn_launch_readiness()` + بطاقة في شاشة الصحة التشغيلية |
| توافق روابط QR | الواجهة تقبل `t` و`token` منذ م2؛ التحويل في GoDaddy بشري |
| بروفة على نسخة من الإنتاج | **بشري** — يوم −14 |
| تدريب الموظفين | **بشري** — المواد أدناه |
| التشغيل المتوازي والإيقاف | **بشري** |

> السكربتات مكتوبة على مخطط مصدر **مُعاد بناؤه** من التدقيق، لا على تفريغ
> حقيقي. أول ما يُفعل في بروفة يوم −14: مواءمة `01-source-adapter.sql` مع
> التفريغ الفعلي. هذا هو الملف الوحيد الذي يُتوقَّع تعديله.

## 1. يوم −14: البروفة الكاملة

```bash
# نسخة من الإنتاج إلى مشروع بروفة، لا إلى الإنتاج الجديد
./scripts/migration/attach-source.sh "$PROD_READONLY_URL" "$REHEARSAL_DB_URL"
psql "$REHEARSAL_DB_URL" -f scripts/migration/01-source-adapter.sql
psql "$REHEARSAL_DB_URL" -f scripts/migration/00-audit-source.sql | tee audit-day-14.txt
```

- [ ] `01-source-adapter.sql` يعمل على المخطط الحقيقي (عدّله حتى يمرّ)
- [ ] تقرير التدقيق محفوظ ومُراجَع مع المالك
- [ ] كل قرار في §4 من 13-migration.md مُتَّخذ ومكتوب في `decisions.sql`
- [ ] حسابات كل الموظفين مُنشأة في المشروع الجديد (الفحص المسبق يرفض بدونها)
- [ ] `02-preflight.sql` يمرّ بلا موانع
- [ ] `03-transform-load.sql` ينجح — **سجّل الزمن الفعلي**
- [ ] `04-migrate-storage.mjs` ينقل كل الصور — سجّل الزمن
- [ ] `05-verify.sql` يمرّ بلا فشل
- [ ] `06-rollback.sql` يمحو كل شيء، ثم يُعاد التحميل بنجاح
- [ ] الأزمنة المقيسة تُحدَّث في جدول نافذة التحويل (§7 من 13-migration.md)

## 2. يوم −7: التدريب

أربع جلسات (التفصيل في 13-migration.md §9). الجلسة الثانية على **أجهزة
الموظفين الفعلية** — هي التي تكشف مشاكل الكاميرا والأذونات قبل الإطلاق.

- [ ] كل موظف نفّذ رحلة كاملة: مسح → استلام → مراحل → فاتورة → دفع → تسليم
- [ ] كل مندوب نفّذ إيداعًا وسجّله بإيصال
- [ ] المالك نفّذ اعتماد تسوية **من هاتفه** لا من حاسوب
- [ ] كل موظف يعرف أين يجد `request_id` وكيف يبلّغ به
- [ ] بطاقة الدور المرجعية (§6 أدناه) مطبوعة وبيد كل موظف

## 3. يوم −3: التجميد

- [ ] لا تغييرات على النظام القديم إلا إصلاحات أمنية
- [ ] `fn_launch_readiness()` يعيد `ready: true` على الإنتاج الجديد
- [ ] بيانات حساب الإيداع مضبوطة (D8)
- [ ] عطل السنة مُدخَلة في `public_holidays` (D9)
- [ ] مفاتيح ثواني الحيّة مضبوطة ومُختبَرة بعملية حقيقية صغيرة
- [ ] جسر واتساب يرسل فعلًا إلى رقم اختبار
- [ ] مفاتيح النظام القديم المكشوفة في المحادثة العامة **مُدوَّرة أو مُلغاة**

## 4. يوم −1 و0: التحويل

يُنفَّذ ليلًا. توقّف الخدمة الفعلي أقل من ١٥ دقيقة.

- [ ] نسخة احتياطية كاملة من النظام القديم — **تُتحقَّق باستعادة تجريبية**
- [ ] النظام القديم للقراءة فقط
- [ ] `attach-source.sh` ثم `run.sh` على الإنتاج الجديد
- [ ] `05-verify.sql` يمرّ — **لا تفعيل للتحويل قبل هذا**
- [ ] مراجعة سجل الترحيل: `select * from fn_migration_log(null)`
- [ ] تفعيل تحويل `myduby.com/qr/*` ← `qr.myduby.com`
- [ ] اختبار بأربعة رموز مطبوعة حقيقية من أربع شقق مختلفة
- [ ] طلب تجريبي كامل من المسح إلى الدفع على الإنتاج
- [ ] إشعار الموظفين بأن النظام الجديد حيّ

### نقطة اللاعودة

تفعيل التحويل. قبله التراجع سكربت؛ بعده نقل يدوي.

## 5. أيام +1 إلى +14: المتابعة

يوميًا في شاشة الصحة التشغيلية:

- [ ] طابور الإشعارات: لا «ميتة»، ولا «عالقة > ٥ دقائق»
- [ ] مدفوعات معلّقة > ساعة = صفر
- [ ] كل تسوية أمس اعتُمدت
- [ ] لا طلب متوقف تجاوز العتبة بلا سبب معروف
- [ ] المهام المجدولة كلها `succeeded`

أسبوعيًا:

- [ ] مطابقة بنكية لكل إيداع
- [ ] مراجعة تقرير استثناءات الإيداع
- [ ] نسبة التحويل في قمع المسح لم تهبط عن خط الأساس

المحطات:

- [ ] +7: إيقاف النظام القديم عن الكتابة نهائيًا
- [ ] +14: نسخة أرشيفية ثم حذف موارد القديم — **لا حذف قبلها**

## 6. بطاقات الأدوار المرجعية

### المندوب

| الموقف | ما تفعله |
|---|---|
| استلام من العميل | امسح رمز الشقة، صوّر الملابس، ينتقل الطلب تلقائيًا |
| التسليم | لا تسليم قبل تسجيل الدفع. امسح، صوّر، أكّد |
| العميل يدفع نقدًا | «استلمت المبلغ نقدًا» — المبلغ يصير في ذمتك حتى الإيداع |
| نهاية اليوم | أودع في الحساب، صوّر الإيصال، أدخل رقمه |
| لم تودع بعد | لن تستطيع تحصيل نقد جديد — أودع أولًا |
| لم يعمل شيء | لا تكرّر. صوّر الشاشة بـ`request_id` وأرسلها |

### المشغّل

| الموقف | ما تفعله |
|---|---|
| تسوية بانتظارك | افتح الإيصال، أدخل المبلغ **من الإثبات** لا من إعلان المندوب |
| فرق في التسوية | لا تعتمد. سجّل السبب واختر «متنازع عليها» |
| دفعة لم تُسجَّل | تحقق من ثواني قبل أي تسجيل يدوي |
| طلب متوقف | تقرير «الطلبات المتوقفة» — تابعه مع المندوب |

### المشرف

- تقرير أداء المندوبين، ومطابقة الإيداعات البنكية، ومراجعة الاستثناءات.
- لا تعتمد تسوية أنت مندوبها — النظام يرفض، وهذه ليست عقبة بل ضمانة.

### مدير النظام

- شاشة الصحة التشغيلية يوميًا أول أسبوعين.
- بطاقة «جاهزية الإطلاق» تختفي وحدها متى مرّ كل بند.
- سجل الترحيل يجيب عن «لماذا صار هذا الطلب كذا؟».
